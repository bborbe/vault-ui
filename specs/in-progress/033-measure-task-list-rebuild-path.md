## Summary

- A `GET /api/tasks` request allocates **~4 MB per selected vault** — 40,565 KB/request on the bare URL (all ten configured vaults) against **329 KB/request** for `/api/vaults`. Allocation is linear in the number of **selected vaults**, not in rows returned, and identity and gzip allocate identically, so the served body really is cached and this cost sits upstream of it.
- The board documents a **bounded** rebuild path for exactly this case, and unit rows prove it works when its precondition holds. So the defect is most likely **reachability**, not the bounded implementation — a page move on this board evidently does not satisfy the precondition.
- **That is a hypothesis, and this spec does not act on it.** Four candidate mechanisms lead to four different fixes, and the board cannot currently say which one fires. This spec makes the board say so — weighted toward one of them: the measurement's **uniformity** rules the two event-shaped board-side premises out as dominant causes, leaves a folder-level mark standing in for a one-file write as the primary suspect, and the instrumentation is built so that suspect can be **confirmed or killed** rather than merely observed.
- **This spec adds instrumentation, reads it, and records the verdict. It changes no behaviour.** Its deliverable is the measurement and the pre-registered decision rule that makes the measurement conclusive.
- The visible consequence, and the baseline the follow-up spec's regression-lock is measured against: the `/api/tasks`-to-`/api/vaults` latency ratio (p50 ≤ 5× in the same ten-sample window) passes 20/20 on the 5-vault filter URL but only **18/20** and **16/20** in two independent readings of the bare URL.

## Problem

The board rebuilds a vault's task-list snapshot — for every task, the uncompleted blockers, the classified session state (a transcript probe), the session-started marker, the registry location, the activity date (a second transcript probe) and the Open Questions section — and that loop costs roughly 4 MB of allocation per vault per request. On the bare URL, which selects all ten configured vaults, that is ~40 MB of allocation per request against 329 KB for the reference endpoint, and it is the most likely source of the GC-assist tail that decides the ratio criterion against the bare URL. The board's own documentation describes a bounded alternative for a page move the page index can attribute to single files, and unit rows prove that bounded path works, so a rebuild of this size on essentially every request means the bounded path is probably not being reached on the live board. **Which** of the page index's documented "cannot bound this set" reasons is responsible is unmeasured, and the candidates lead to different code sites, so a fix written now would be a guess. This task has already paid twice for guessing: two earlier hypotheses about this same residual were proposed and retracted after measuring. This spec buys the measurement instead.

## Goal

The board can say, from its own metrics, what kind of task-list rebuild ran, why any full rebuild ran, and why the page index could not bound a changed set; a named benchmark can attribute the rebuild's allocation to a section rather than to the rebuild as a whole; and a recorded reading over a defined protocol names exactly one mechanism — or records that none of the named mechanisms applies — **before any behavioural change is proposed**. Nothing about how the board serves a request changes: the invalidation stays exactly as it is (it is correct, and the revision really does move on this board) and the per-task work stays exactly as it is.

## Non-goals

- **No behavioural change of any kind.** This spec adds counters, a benchmark and a document. The invalidation, the rebuild's choice of path, the per-task work, the decoded JSON, the wire shape, the body cache, the page index's parse model and its store, and every endpoint are unchanged.
- **No remedy is implemented here.** The reading's verdict is recorded and the follow-up spec is authored from it. The candidate implications in Desired Behavior 4 are the decision rule's semantics, recorded so the verdict is unambiguous — they are not deliverables of this spec.
- **Do NOT disable, weaken or gate the invalidation.** The revision moves on essentially every request because roughly twenty live sessions write this vault continuously, and the store must still rebuild when its input moved. The defect, if any, is that a rebuild which *could* be bounded is not — never that a rebuild fires.
- **Do NOT trim or weaken the per-task work** in the rebuild — the uncompleted blockers, the session classification, the session-started marker, the registry location, the activity date and the Open Questions section. That work is legitimate when the pages genuinely moved.
- Do NOT reduce the payload, change the body cache, change the `Content-Encoding` / `Vary: Accept-Encoding` negotiation, or change the decoded JSON.
- Do NOT scope the invalidation to a single vault — the bare query selects every configured vault by construction, so a per-vault scope alone leaves the bare URL paying exactly as it does now.
- Do NOT move the rebuild off the request path, add a timer, or add a configuration key.
- Do NOT change the page index's parse model, its on-disk store, cold start, or the endpoints other than `/api/tasks` (`/api/assignees`, `/api/vaults`, `/api/goals`, `/api/topics`).
- Do NOT add a cache, a memo or a knob for the ~615 KB per-request fixed overhead — a separate concern, recorded as a finding only.
- Do NOT add a new scenario — see the note under Acceptance Criteria.

## Assumptions

- The allocation table below is a true per-request measure of the rebuild cost: the burst is warm, `go_memstats_alloc_bytes_total` is monotonic, and the **linear-in-selected-vaults** shape is what distinguishes a per-vault rebuild from a per-request copy.
- The revision moves on essentially every request. The measurement's per-vault shape supports a rebuild per vault per request; it does not by itself identify the kind of rebuild, which is what the counters add.
- The existing unit rows prove the bounded path works **when its precondition holds**. This spec measures the reachability assumption rather than relying on it.
- The board's admin metrics endpoint at `127.0.0.1:9090` is the measurement surface and is reachable from the host.
- An instrumented build cannot run beside the live board: the admin port is a hardcoded constant in `main.go`, so a second instance cannot bind it. The live half of the reading is therefore a deploy, with its own restart consent.
- A fixture-based benchmark attributes the allocation **proportionally** between the rebuild's sections, not in the live magnitude. The live magnitude comes from the allocation table; the benchmark says which section dominates the per-vault cost.

## Reproduction

**Config.** The local board as deployed by launchd: label `com.github.bborbe.vault-ui`, binary `~/Documents/workspaces/go/bin/vault-ui`, serving on `127.0.0.1:8000`, admin and metrics on `127.0.0.1:9090`, ten vaults configured in `config.yaml`. Deployed version at the time of measurement: **v0.96.1**.

**Command sequence.** For each query: read the allocation counter, run a discarded warm-up, run a 100-request warm burst, read the counter again, divide by 100.

```bash
alloc() { curl -s --noproxy '*' 'http://127.0.0.1:9090/metrics' \
            | awk '/^go_memstats_alloc_bytes_total/{print $2}'; }
burst() {  # $1 = tasks URL, $2 = label
  curl -s --noproxy '*' -o /dev/null "$1"
  b=$(alloc)
  for i in $(seq 1 100); do curl -s --noproxy '*' -o /dev/null "$1"; done
  a=$(alloc)
  awk -v a="$a" -v b="$b" -v l="$2" 'BEGIN{printf "%-28s %6d KB/req\n", l, (a-b)/100/1024}'
}
burst 'http://127.0.0.1:8000/api/vaults'                          '/api/vaults (control)'
burst 'http://127.0.0.1:8000/api/tasks?vault=private-personal'     'tasks, 1 vault'
burst 'http://127.0.0.1:8000/api/tasks?vault=private-agent&vault=private-personal&vault=seibert-agent&vault=seibert-brogrammers&vault=seibert-personal' 'tasks, 5-vault filter'
burst 'http://127.0.0.1:8000/api/tasks'                            'tasks, bare (all 10)'
burst 'http://127.0.0.1:8000/api/tasks?vault=__nonexistent__'      'tasks, no vault selected'
```

**Observed evidence (2026-10-14, v0.96.1, recorded in the owning task's `# Progress`).**

| query | vaults selected | alloc / request | gc cycles / 100 req |
|---|---|---|---|
| `/api/vaults` (control) | — | **329 KB** | +0 |
| `/api/tasks?vault=private-personal` | 1 | **4,062 KB** | +1 |
| 5-vault filter URL | 5 | **31,954 KB** | +10 |
| bare `/api/tasks` | all 10 | **40,565 KB** | +12 |
| bare `/api/tasks`, `Accept-Encoding: identity` | all 10 | **40,547 KB** | +11 |
| `/api/tasks?vault=__nonexistent__` (50 requests) | 0 | **615 KB** | — |

**Two conclusions.** Allocation is linear in the number of selected vaults (~4 MB each) and not in rows returned: the bare query returns 2.9× the rows of the 5-vault filter but allocates only 1.27× as much. And identity and gzip allocate identically, so the response body really is served from the existing body cache and the encode is off the request path — the caching work (specs 031 and 032) is correct and is not what this spec touches.

**The visible consequence.** The `/api/tasks`-to-`/api/vaults` latency **ratio** criterion — p50 ≤ 5× in the same ten-sample window — passes on the 5-vault filter URL in 20/20 windows (median 3.63×) but only **18/20** (median 3.81×, max 5.23×) and **16/20** (median 4.03×) in two independent readings of the bare URL. The median sits at 3.8–4.0× against a 5× bound, so the criterion is decided by its tail. A peer probe excluded host load and a single stop-the-world GC as the cause and identified GC assist on a heavy allocator as the likely tail mechanism. This spec does not change that reading; it records it as the baseline the follow-up spec's regression-lock is measured against.

**Verified in the source** (symbols, not line numbers — they drift):

1. `pkg/board/tasks.go` `buildTaskRows` — per task in every selected vault: `uncompletedBlockers`, `session.ClassifySessionState` (with `b.transcriptProbe()`), `sessionStarted`, `signals.RegistryLocation`, `activity.ComputeActivityDateWith` (a second transcript probe) and `openQuestionsFor`. Over ~2,712 tasks that is the per-vault cost, and it is the loop the benchmark must attribute section by section.
2. `pkg/board/snapshot.go` `List` — a key rebuilds when `revision != e.pageRevision || generation != e.sessionGeneration`. The cheaper kinds are chosen top-down: a session-only move takes the **refresh**; a page-only move takes the **patch** *only if* `ChangedPagesSince` reports it can bound the set; a move of both at once takes the **full build**.
3. `pkg/board/snapshot.go` `runBuild` — a full rebuild, a patch and a refresh all succeed the same way, and the published-rows signal advances only when the rows differ.
4. `pkg/board/tasks.go` `refreshTaskRows` — a session-only move re-derives the session fields **for every row**, two transcript probes each; it avoids the page-derived work, not the per-row work.
5. `pkg/board/tasks.go` `patchTaskRows` — a nominally-bounded build can perform a full rebuild, because the patch returns the full build for the whole key from **two** sites: a changed page with **no held row** (`case present:` in the first loop), and a changed page the snapshot holds but the list operation dropped (`itemByName[name]` missing in the second loop). Two different states, two labels.
6. `pkg/pageindex/pageindex.go` `ChangedPagesSince` — returns `ok == false` for: an unknown key; a revision ahead of the key's current one; a revision the retained change window no longer covers (`len(e.changeLog) == 0 || e.changeLog[0].revision > revision+1`); and any advance in the window recorded as unbounded. It reports only `ok`, never **why**, which is the gap the new page-index counter closes.
7. `pkg/pageindex/pageindex.go` `maxChangeLog = 64` — the retained change window is a fixed count of advances per key.
8. `pkg/pageindex/pageindex.go` `MarkDirty` (folder-level, unbounded), `MarkFileDirty` (one file, bounded — and it **widens to a folder-level mark** when its exactness rule fails: an unknown key, a key with no published snapshot, a name that is not a plain base name, a name the snapshot does not already hold (`!snapshotHasName`), or a file missing on disk at mark time — and the snapshot condition is the one a newly created file always trips, since the snapshot is the last read's page list), `ForceReload` (unbounded); `pkg/pageindex/pageindex_build.go` records a publication's advance as bounded only when the read was not a full build and the key already had a snapshot (so a key's first publication is unbounded); `pkg/pageindex/pageindex_file.go` `RefreshFile` records a watcher event as bounded, naming the file.
9. `pkg/mutations/mutations.go` `markVaultDirty` — the synchronous write routes mark their vault's **tasks and goals keys at folder level**, which is an unbounded advance; `docs/page-index.md` counts those sites at eight.
10. `pkg/sessionsnapshot/snapshot.go` — `SessionRefreshInterval = 60 * time.Second` and `RefreshOnce` advances the generation on every tick whether or not anything changed.
11. `pkg/pageindex/metrics.go` — the package already exposes a labelled counter (`vault_ui_page_index_files_read_total{reason}`), which is the pattern the new counters follow. **No `vault_ui_board_*` series exists today**, so every counter this spec adds is new.

## Expected vs Actual

**Expected.** Per `docs/page-index.md` § *Task-list snapshot*: "**Row patch.** A rebuild may re-derive a bounded set of rows instead of all of them. When only the page revision moved, the page index can name the pages whose parsed form changed … and the rebuild re-derives exactly those rows." A page move on a vault written by ordinary single-file writes is the documented normal case for that bounded path.

**Actual.** On the deployed board, a request that selects one vault allocates ~4 MB — the signature of a **full rebuild**, not of a bounded row re-derivation — and the cost scales with the number of selected vaults. The bounded path is implemented and unit-tested, so on this board its precondition is evidently not satisfied; **which** part of that is true is unmeasured.

**Why this is a bug.** It contradicts documented behavior: the board documents a bounded re-derivation for exactly this case, and the request path pays the full per-vault cost instead. It also holds back the metric the body cache shipped to improve — the cache is warm and correct, but the rebuild it sits downstream of runs on essentially every request — which is why the ratio criterion fails on the bare URL's tail while passing every window on the filtered URL.

**Workaround.** None user-side. The operator-side mitigation is the one the probes already use: sample `/api/vaults` in the same window and read the median, which passes while individual windows do not. Restating the criterion is a new operator decision and is out of scope.

## Open Questions

These are the questions the reading exists to answer. They are unresolved until it runs, and this spec deliberately does not resolve them by argument.

- **Which mechanism fires** — a folder-level mark standing in for a single-file write (the primary suspect, per Desired Behavior 4's prior), a page move colliding with the session-generation tick, a retained window the board's write rate overruns, or a changed page with no held row. The counters and the pre-registered decision rule separate them, and the four `folder_mark_widened_*` labels separate the primary suspect's own sub-causes.
- **Which call path carries the folder-level mark on the request cadence** — the prior's one unestablished link, stated in full in Desired Behavior 4. The reading must show it, not just that a folder-level mark dominates.
- Whether the bounded path is missed **at all**. If the reading shows the bounded path is taken and the allocation is still ~4 MB per selected vault, the cost is the documented per-task work, which this spec must not trim — and the finding returns to the operator rather than becoming a remedy.
- Whether the follow-up remedy belongs in `pkg/pageindex` (the mark sites and the change window) or only in `pkg/board` (the store's choice of path). The two are different specs' worth of work.
- Whether the benchmark's fixture is representative enough for its proportional attribution to transfer to the live magnitude. The reading cross-checks it against the allocation table's per-vault figure.
- Whether the ~615 KB per-request fixed overhead is worth its own spec — recorded as a finding here, not scoped.
- Whether the ratio criterion's missing load band makes it non-reproducible as written. The criterion is strongly load-dependent and names no band; the operator has ruled that its wording stays as it is, so every reading this spec takes carries its **load band** and its **slow-tail values** alongside the median.
- Whether the live half of the reading can be taken at all: it needs a deployed instrumented build, and the admin port is a hardcoded constant, so it needs a board restart with its own consent. If that is refused, the reading stops at its container half and no verdict is produced.

**Where the falsifier lives.** AC1 and AC2 are **declaration** requirements: they establish that the labels exist and that the paths those labels name are covered by real, passing rows. They deliberately do not assert a per-label delta — an exact-delta assertion over a sixteen-label surface is one more place a fake instrumentation can hide, and the negative form of it ("and no other label advances") is one more place a correct implementation can trip. **That trade is stated rather than hidden.** With the per-label deltas gone, the mechanical defense against an instrumentation that exists but never counts is weaker, and the device that replaces it is the reading: AC5 requires the raw metric output pasted verbatim rather than summarised, so a reader sees the series themselves, and a non-zero delta on the deployed board, which fails an instrumentation that never counted. **Attribution is therefore audited by a human reading raw output, not asserted mechanically** — a rebuild attributed to the branch the store chose rather than to the work it performed is caught by that reading and by nothing else in this spec. **AC6 and AC7 are fences, not discriminators**: they fail a change that alters behaviour, and a no-op passes them by construction — which is why they are not what decides whether this spec's work was done. This is stated so that a reader knows exactly what is and is not defended here.

## Desired Behavior

1. The board classifies every task-list rebuild by the **kind of work it performed** — a full build, a row patch, or a session refresh — and attributes **every full rebuild to its cause**, and exposes both on the admin metrics endpoint. A full rebuild performed *inside* the patch path is attributed to its own cause and not to the patch, so a nominally-bounded build that fell back cannot be read as the bounded path being taken.
2. The page index reports **why** it could not bound a changed set, one reason per documented case, on the admin metrics endpoint, so a refused bound can be told apart from a bound that was never attempted — and, for the primary premise, so a **folder-level mark a write route issued outright** can be told apart from a **`MarkFileDirty` widening**, which are different code sites and different fixes. Where one read's window holds **more than one** unbounded advance — an explicit folder mark followed by a widening, say — the reason reported is the **earliest** one, by the precedence rule in Constraints, so a reading consumes a single deterministic answer rather than a set.
3. A benchmark in `pkg/board` measures the allocation of each section of the rebuild — the vault list, the row construction, the blockers, the session classification, the session-started marker, the registry location, the activity date, and the Open Questions section — so the reading can attribute the per-vault cost to a section rather than to the rebuild as a whole. The sections are a **named split with an explicit residual**: their figures plus that residual account for the whole function's allocation on the same fixture, so the attribution is a split of the cost and not a list of names.
4. The decision rule below is recorded in `docs/task-list-rebuild-cost.md`; after the reading, the same document carries the reading and its verdict.

   **The pre-registered decision rule.** Read R = (the rebuild-kind deltas, the full-rebuild-reason deltas, the page-index unbounded-reason deltas, the allocation table, the benchmark attribution) over the protocol.

   **The prior this rule is weighted by — a prior, not a proof.** The measurement is **uniform**: ~4 MB on every request, across all ten vaults, over a 100-request burst. That shape is itself evidence, and it rules the two board-side premises out as *dominant* causes because both are event-shaped rather than per-request: `both_moved` needs a page move to coincide with the session-generation tick, and the generation advances once per successful refresh (≥60 s), so it can touch at most about one request per minute; `new_page_no_held_row` fires per newly created page, a few per minute across the vault, not per request. `window_not_retained` needs more than 64 revision advances **on one key between two consecutive requests**, and the board re-reads on every request, so on a burst fired in about half a second that would need >64 advances in the milliseconds between two of the 100 requests. That leaves **`folder_mark` as the primary suspect**, and its mechanism is readable from source: `MarkFileDirty` widens to a folder-level `MarkDirty` when the key's snapshot does not already hold the page name (`!snapshotHasName(e.snapshot, stripped)`), and for a newly created file that is always true — the snapshot is the last read's page list and cannot hold a file that did not exist then. A folder-level `MarkDirty` records `recordChangeLocked(nil, false)`, an explicitly unbounded change, so `ChangedPagesSince` returns `ok=false` and the store takes the full rebuild.

   ⚠️ **The prior's one unestablished link, named so a reader can check it.** `MarkFileDirty`'s callers are the board's write routes, and each names an item id for a file it is editing, while a file created by a live session reaches the index through the **watcher** — whose per-file path (`RefreshFile`) records a *bounded* change, and whose folder fallback (`Refresh` → stat-diff) is also bounded on an established key (`bounded = !full && e.hasSnapshot`, and `full` is set only for a cold build, a reload, or a key with no baseline). So a folder-level mark lands on the request cadence only if a write names a file the snapshot does not yet hold, or if a write route's own folder-level mark fires between requests. **Which of those carries the cadence is exactly what the reading must show**; the prior says `folder_mark` dominates, not which of its sub-causes does. This is why Desired Behavior 2 separates the folder-level causes from each other instead of reporting one `folder_mark` label.

   **The rule, weighted by that prior.**

   - **primary** — the page-index dominant reason is one of the `folder_mark_*` reasons ⇒ the premise **P2** — a folder-level mark stands in for a write that touched one file; the sub-cause names which code site carries it.
   - **unlikely, recorded so it is not equally weighted** — `kind="full"` accounts for the rebuilds, `full_rebuilds_total{reason="changed_set_unbounded"}` dominates, and the page-index dominant reason is `window_not_retained` ⇒ the premise **P1** — the retained change window does not cover the span a read can fall behind by. Unlikely on this protocol: more than 64 advances on one key between two consecutive requests, per the prior above.
   - **unlikely, recorded so it is not equally weighted** — the board's dominant reason is `both_moved` ⇒ the premise **P3** — a page move coinciding with a session-generation move is never patched. Unlikely as a dominant cause: event-shaped, at most about one request per minute.
   - **unlikely, recorded so it is not equally weighted** — the board's dominant reason is `new_page_no_held_row` ⇒ the premise **P4** — a changed page with no held row forces a full rebuild from inside the patch. Unlikely as a dominant cause: event-shaped, a few per minute across the vault.
   - `kind="patch"` or `kind="refresh"` accounts for the rebuilds and the allocation is still ~4 MB per selected vault ⇒ the bounded path **is** taken and the remaining cost is the documented per-task work: record that finding and stop.
   - any other reading (for example `cold_key` dominating, or no rebuilds at all) ⇒ record it and stop.

   **The branches are ordered and the first match wins.** They can co-occur: a folder-level mark can land in the same read window as a session tick or as a new page, and the same burst can show a `folder_mark_*` reason alongside a `both_moved` or `new_page_no_held_row` count. The ordering resolves that in favour of the primary branch — the one whose sub-cause the instrumentation exists to name — and a reader must take the first matching branch rather than averaging the branches or reporting two. The `unlikely` branches are consulted only when no `folder_mark_*` reason dominates.

   This rule is the decision record, and this spec implements none of it. The one-line implication each premise carries is recorded so the verdict is unambiguous and so the follow-up spec starts from the decision rather than re-deriving it: **P1** ⇒ the window must cover the span a read can fall behind by; **P2** ⇒ the folder-level mark must be narrowed at its source — where the widening is `!snapshotHasName`, the mark stays **file-level for a file that exists on disk but is not yet in the snapshot**, one guard in `MarkFileDirty`, and where it is a write route marking the folder outright, that route marks the file it touched; **P3** ⇒ the page-derived rows must be patched and the session fields refreshed rather than rebuilt in full; **P4** ⇒ the missing row must be derived and spliced. P2 is the one whose fix is a single guard rather than a structural change, which is part of why it is the primary suspect, and the sub-cause the reading names says which guard. Which of those, if any, is the follow-up spec's scope is decided by the verdict and by the operator — not here.
5. Nothing about how the board serves a request changes: the decoded JSON, the wire shape, the body cache, the invalidation, the rebuild's choice of path, the per-task work, the page index's parse model and its store, and every endpoint are as they are today.

## Constraints

- **This spec changes no behaviour.** The invalidation stays: the store must still rebuild when its input moved. The per-task work stays: a rebuild whose pages genuinely moved still classifies the session state, computes the activity date, reads the blockers and derives the Open Questions for every affected task. The new code is counters, a benchmark and a document.
- The invalidation model is the one documented in `docs/page-index.md` § *Task-list snapshot*. This spec does not restate it, does not change it, and does not change which path a rebuild takes.
- The `IndexRevisions` interface the board consumes is unchanged: `Revision`, `ChangedPagesSince` and `ListPages` keep their signatures, so the page index reports its reason through a counter rather than a changed return value.
- `pkg/pageindex`'s `pageChange` is internal, so carrying a cause on it is not an interface change.
- **One refused bound reports one reason: the earliest unbounded advance in the window.** A window can hold several — an explicit folder mark followed by a widening is the ordinary case — and the reported reason is the one with the **lowest revision**, so the answer is deterministic and does not depend on what landed after the bound first became impossible. The counter therefore reports at most one reason per refused bound, and its totals are counts of **refusals by cause**, never of advances. A reading must not sum the reasons against the request count and expect them to match.
- **The widening path must record its own cause, not reuse the explicit mark's.** `MarkFileDirty` reaches the folder level by calling the same `MarkDirty` the write routes call, so an implementation that lets the widening record the explicit folder-level cause cannot tell the two apart — and the reading would then be unable to confirm or kill the primary premise (Desired Behavior 4). The four `folder_mark_widened_*` labels must be produced at the widening sites, and `folder_mark_explicit` only where a caller marked the folder outright.
- **Each counter is incremented once per rebuild, never per row**, so the instrumentation adds no per-request allocation proportional to the vault's task count. The per-request fixed overhead stays at its 615 KB baseline.
- The new counters are fixed names, pre-initialised at boot so an alerting rule sees them from boot, incremented outside any lock the request path holds, and carry a fixed enum of labels so a client cannot grow their cardinality. No metric is read on the request path.
- The container half of the reading must be reachable **without a deploy** — the mechanism rows and the benchmark. The live half needs an instrumented build, and `adminListen` is a hardcoded constant in `main.go`, so a second instance cannot run beside the live board: the live reading is operator-rung and its restart carries its own consent.
- The ratio criterion names no load band and is strongly load-dependent. Its wording is not changed; every reading this spec takes carries its load band and its slow-tail values alongside the median.
- `CHANGELOG.md` gains one `feat:` entry under a `## Unreleased` heading, naming the new counters.
- Every existing `make test` row in `pkg/board` and `pkg/pageindex` keeps its assertions, since no behaviour changes. The rows this spec leans on include `builds once and serves the identical slice on a warm read`, `rebuilds when the page-index revision moves`, `rebuilds when the session generation moves`, `keeps the previous rows when a rebuild fails and retries on the next read`, `advances the published-rows signal only when a rebuild changes the rows`, `does not clear an invalidation recorded while a build was in flight`, `never mixes two published row sets under a concurrent reader`, `bounds a hung build by the timeout`, `keeps different keys independent`, `re-derives only the changed rows and never rebuilds`, `rebuilds in full for a folder-level mark`, `takes the session-only refresh when only the generation moves`, `rebuilds in full when the page revision and the generation both move`, `keeps the previous rows when a patch fails and retries the next read`, `serves only the changed pages it was given`, `re-derives only the changed row without touching the vault seams`, `carries the held session fields onto the re-derived row`, `drops the row of a changed page that is gone`, `falls back to the full build for a changed page with no held row`, `recomputes a dependent row's blockers when its blocker's page changes`, and `recomputes the session-started marker of a changed row`.

## Failure Modes

| Trigger | Expected behavior | Recovery | Detection |
|---|---|---|---|
| A counter increment races a concurrent rebuild of the same key | the counters are process-wide monotonic counters, so a racing rebuild is counted as its own rebuild and the totals may exceed the request count; the reading uses **deltas** and never assumes one rebuild per request | none needed — the counters are safe under concurrency | `go test ./pkg/board/... ./pkg/pageindex/... -race` passes; the reading's per-request figure is a ratio, not an identity |
| The instrumentation's own increments perturb the measured path | each counter is incremented once per rebuild, never per row, so the per-request fixed overhead stays at its 615 KB baseline | — | the re-measured allocation table's no-vault-selected row |
| A counter is read while the store mutex is held | the request path gains a metric cost | read the counters off the path | the allocation table's fixed-overhead row |
| A metric series is missing at boot | an alerting rule sees nothing | pre-initialise every label combination at boot | `curl …/metrics \| grep -c` |
| A full rebuild happens inside the patch path | attributed to the site that caused it — `new_page_no_held_row` or `patch_page_not_listed` — never to the patch, and never collapsed into one label | — | the counter's own label |
| A read falls behind by more than the retained window | the bounded path is refused and the key rebuilds in full | — | `vault_ui_page_index_changed_pages_unbounded_total{reason="window_not_retained"}` |
| The benchmark's fixture is unrepresentative | the attribution is proportional and may not transfer to the live magnitude | cross-check it against the allocation table's per-vault figure, and record both | the document carries both the benchmark output and the live table |
| A genuine row change lands during the protocol | the response is not byte-identical to its predecessor and is excluded from the reading | — | the byte-identity check inside the protocol |
| A rebuild fails (a vault read error) | the previous rows keep serving; the error is logged with the key; the next read retries | automatic on the next read | the log line naming the key; the existing failure rows |
| The live reading cannot be taken (no restart consent) | the verdict is not produced and no remedy is authorised; the container half stands as the record | return to the operator | `docs/task-list-rebuild-cost.md` carries no live reading and no verdict |
| The reading supports none of the named premises | the document records the stop; no remedy is implemented | return to the operator | the document's verdict section names no premise |

The rebuild reads vault files and spawns no process of its own beyond the existing transcript probe; there is no network call and no external service, so external-unavailability and rate-limiting rows do not apply beyond the vault-read failure row above. There is no partial-progress state: a rebuild publishes all rows or none.

## Security / Abuse Cases

- The route is read-only and unauthenticated, and this change adds **no request input**. Both counters and the page-index reason counter derive entirely from server-side state — the page index's per-key revision, its change log, and the store's own path choice. A client cannot force a full rebuild, force the bounded path, or suppress a rebuild, and it cannot influence any counter.
- **This spec introduces no new correctness or staleness risk**, because it changes no behaviour: no mark is narrowed, no window is widened, no path is changed. The staleness risk belongs to the follow-up remedy and must be fenced there.
- **Trust boundary: none new.** No new input is parsed; the handler parses the query exactly as it does today, and the query does not affect the rebuild — the rebuild is per key, not per query.
- **Cardinality is bounded.** Both counters carry a fixed enum of labels; a client cannot grow them. Every label combination is pre-initialised, so the series set is fixed at boot.
- **What can hang or retry forever: nothing new.** A rebuild is bounded by the existing snapshot build timeout, and a failed build is retried by the next read without looping.

## Do-Nothing Option

Do nothing and the hypothesis stays unmeasured: the board has no way to say which rebuild ran or why, so the next attempt at this residual is another guess — and this task has already retracted two guesses about it after measuring. The ratio criterion stays unmet on the bare URL (18/20 and 16/20 in two independent readings), so the sibling task's SC1 cannot be ticked and the goal hand-off it gates stays blocked, while the bare URL keeps allocating ~40 MB per request against 329 KB for the reference endpoint. The board remains usable — the absolute bar (warm p50 < 50 ms on the filtered URL) is met with roughly 9× headroom and the decoded payload is unchanged — so the cost of doing nothing is a criterion decided by its tail, plus an unmeasured residual that will keep attracting guesses.
