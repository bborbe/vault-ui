# Card rendering

Every card on the board — task, goal and topic — is produced by one component,
`Card` in `frontend/src/components/Card.tsx`. The component contains no
per-kind markup and no branch on a kind name. A kind contributes only data and
capabilities, through two extension points:

1. **Its entry in `CARD_CONFIG`** (`frontend/src/model.ts`) — which affordances
   the kind carries and how its board places it.
2. **Its API response** — the card reads the fields the kind's endpoint serves
   (`TaskResponse`, `GoalResponse`, `TopicResponse` in `frontend/src/types.ts`,
   generated by `tygo` from `pkg/api`).

The React port replaced the vanilla-JS `createCard(kind, item)` template and its
three mappers; the single-template rule it established still holds.

## `CARD_CONFIG` fields

| Field | Meaning |
| --- | --- |
| `draggable` | Whether the card is draggable and writes a phase on drop. `true` for tasks only: the board writes a task's phase, while a goal's or topic's phase is owned by `vault-cli`. |
| `menu` | Whether the `⋮` lifecycle menu renders. Also what turns the status controls off for a kind: every status action (complete, defer, abort, hold, resume) lives in that menu. |
| `detail` | Whether the `📋` button opens the topic detail modal. Topic only. |
| `assigneeClickable` | Whether the assignee badge is a filter control (`active` state, click toggles the filter) or plain text. `false` for topics: no topic assign route exists. |
| `greyWhenTerminal` | Whether a terminal card (`completed` / `aborted`) gets the dimmed `recently-completed` class. `false` for tasks, which grey through the server's 8-hour `recently_completed` flag; `true` for goals and topics, whose responses carry no such flag. |
| `idDataset` | The `data-*` attribute carrying the item id (`taskId`, `goalId`, `topicId`). |
| `kindDataset` | Value for `data-kind`, or `null` to omit it. |
| `vaultDataset` | Whether `data-vault` is set. Topic only, because a topic name is not unique across vaults. |
| `extraClass` | Extra class appended to the base `task-card` class (`''`, `goal-card`, `topic-card`). |
| `titleLinkExtraClass` | Extra class on the title anchor (`''`, `topic-title-link`). |
| `holdTitle` | `title` attribute of the hold badge. |

## What every card renders

| Row | Markup |
| --- | --- |
| Title | `.card-content > h3.task-title`; the anchor links to the in-app page view when the Obsidian deep link resolves (`pageUrlFromObsidianUrl`), else to `obsidian://`; the Obsidian hand-off is the sibling `.obsidian-handoff` anchor (`↗`). |
| Blocked | `.card-blocked` with the `.blocked-badge` naming every still-open blocker; clicking jumps to that card on the board. |
| Hold reason | `.card-hold-reason` when claude-wrapper holds a flagged, open row; a reason the card already says is suppressed. |
| Jira | `.card-jira` from the page's own `jira:` value, falling back to a key in the title. |
| Footer left | Flag button, hold badge, assignee badge (or `+ Assign to me`), priority chip, mode pill, and — for topics — the detail button. |
| Footer right | Activity age, then the session control. |

## The session control

One control serves all three kinds, in this order:

1. A **terminal** card (`completed` / `aborted`) renders the `✓ Done` chip and
   nothing else. The gate sits first, so a closed row offers no session control
   even when it still carries a `claude_session_id` — Live means an active
   session, not a recorded id.
2. A launch marker (`claude_session_started`) or a per-tab optimistic start
   renders `⏳ Starting…`; clicking it takes over the in-flight launch.
3. `session_state === 'live'` renders the `.live-badge` (take-over affordance);
   the `.jump-btn` renders only when `jump_pane` is set, so a headless session
   offers no jump that would fail.
4. A recorded session renders `▶ Resume` (disabled while `indeterminate`).
5. Otherwise `▶ Start`.

## Layout

`.card-content > h3.task-title`, then the badge rows, then
`.card-footer > .card-footer-left` + `.card-actions`. `.card-actions
{ margin-left: auto }` (`frontend/src/styles.css`) pushes the action group to
the right edge. No card kind renders a `.status-badge`: the column is the phase.

## Escaping

React escapes every interpolated value, so the old `escapeHtml` / `escapeJsAttr`
pair is gone with the string-built markup. A page-derived value never reaches a
raw HTML sink: the component has no `dangerouslySetInnerHTML`.

## Test coverage

- `frontend/src/model.test.ts` — the pure contract: column mapping, sorting,
  urgency tiers, Jira extraction, the page-URL conversion, bucketing, and the
  URL/localStorage state.
- `frontend/src/App.test.tsx` — render-level: the fetched rows, the page-view
  link, the banners and the error state.
- `e2e/` — the parity oracle. The Go/Playwright suite asserts the class hooks
  (`.task-card`, `.goal-card`, `.topic-card`, `.task-title-link`, `.menu-btn`,
  `.start-btn`, `.jump-btn`, `.live-badge`) and the behaviour behind them. A
  card change is verified by running `make e2e`; Vitest alone is not proof that
  the page renders.

## Adding an affordance

1. Edit `Card.tsx` once, gated on a `CARD_CONFIG` field.
2. Add the field to each `CARD_CONFIG` entry that wants it; a kind without one
   renders nothing.
3. Read the data from the kind's API response — extend the Go wire struct and
   regenerate `types.ts` with `make types` if the field is new. Never branch on
   the kind inside the component.
4. Add a Vitest assertion for the pure part and an e2e assertion for the
   rendered part.
5. Load the board and confirm every card kind that carries the affordance
   renders it.
